# Проверки качества: что они доказывают

Требования и численные бюджеты определены в [AGENTS.md](../AGENTS.md#качество).
Подробные границы — в [контрактах модулей](contracts/MODULE_BOUNDARIES.md).
Здесь описана связь требований с инструментами, а не второй набор правил.

| Проверка | Что контролирует | Чего не доказывает |
|---|---|---|
| Kotlin compiler / Android Lint | Типизацию, предупреждения как ошибки, диагностику Android | Корректность всех пользовательских сценариев |
| Detekt | Структурные бюджеты из detekt.yml; текущая область src/main и src/test | Что дробление классов осмысленно; полный охват androidTest |
| KtLint | Kotlin и Gradle Kotlin DSL в области task | Корректность архитектуры или поведения |
| verifySourcePolicy | Подавления/baseline, перечисленные запрещённые конструкции, imports и отдельные feature/host границы | Все транзитивные вызовы, thread safety, реальную отмену HTTP и плавность |
| verifyReleaseMetadata | Согласованность реестра версий, bundled changelog и рабочего manifest | Что APK уже опубликован или подписан нужным ключом |
| Unit tests | Поведение в проверенных случаях, ошибки/отмену при соответствующих assertions | Поведение настоящего Android по одному fake/harness |
| device-smoke | Instrumented tests выбранных модулей в Android runtime | Полное покрытие устройства, работу внешнего сервиса или performance PASS |

## Одна точка запуска

Команды и требования к среде находятся в [DEVELOPMENT.md](DEVELOPMENT.md).
`local-check` выполняет debug/release assembly и `qualityCheck`; последний зависит
от `check`/Detekt production-модулей, KtLint, source policy и release metadata.
Gradle получает `--warning-mode=fail`. Detekt, KtLint и Lint остаются без baseline;
правила и область исполнения этим документационным патчем не меняются.

Сфокусированная проверка полезна для обратной связи, но её результат не называется
`LOCAL CHECK: PASS`. Проверки релизного процесса описаны отдельно в
[RELEASE_PROCESS.md](RELEASE_PROCESS.md#проверка-изменений-процесса).

## Известные риски и ручное ревью

- Сложность native-плеера, seek/отмена/аудиосинхронизация остаются риском;
  [карта владельцев и проверок](features/PLAYER.md) не означает закрытие долга.
- Статический guard не проверяет осмысленность границ внутри app. Перед выделением
  модуля нужен разбор зависимостей и ресурсов, а не только подсчёт файлов.
- Много тестовых файлов само по себе не доказывает тестовый долг. Дубликаты,
  хрупкость и цену поддержки нужно устанавливать по конкретным сценариям.
- Для hot path нужен [release-замер](contracts/PERFORMANCE.md), не субъективное
  впечатление, успешная сборка или исторический лог.

Фактический статус текущей работы записывается в её отчёте, не в вечном документе
«последний PASS». Исторические результаты находятся в [history](history/README.md).
