# Работа с проектом и проверки

Сборочная среда: JDK 25 (gradle/gradle-daemon-jvm.properties), SDK Platform 37,
NDK 29.0.14206865 и CMake 3.22.1. Приложение рассчитано на Android 11+ и ARM64.
Краткое открытие проекта — в [README](../README.md); обязательные правила —
[AGENTS.md](../AGENTS.md). Все команды ниже выполняются из корня проекта.

## Изменение и тесты — один патч

Каждое изменение поведения сопровождается автоматическими тестами в том же
патче, по [правилу качества](../AGENTS.md#качество). Для бага сначала воспроизвести
ошибку тестом, затем проверить его падение на старом коде и прохождение на новом.
Проверять основной сценарий, границы и применимые ошибки/отмену; тестировать
поведение, а не наличие строк реализации. Если меняется декларативный контракт
(например, Android Manifest), дополнить поведенческие тесты проверкой его
согласованности. Отдельно записать выполненные команды, результаты и ограничения.
Фокусные тесты помогают разработке, но не заменяют полный порядок ниже.

## Совместимость Gradle

Wrapper закреплён на Gradle 9.6.1 с проверкой SHA-256. Gradle 9.8.2 объявляет
`Configuration.setVisible` устаревшим; его вызывают используемые Kotlin/Android
плагины. Версия 9.6.1 выбрана как совместимая с текущим AGP 9.4.1 и Kotlin
2.2.10. Mockito 5.20.0 содержит Byte Buddy 1.17.7 с поддержкой Java 25;
прежний Byte Buddy 1.15.4 не мог создавать inline-моки в тестах на Java 25.
Требование `--warning-mode=fail` сохранено; диагностика не подавляется.
При обновлении плагинов и wrapper полный строгий сценарий выполняется заново.

## Обязательный порядок после каждого патча

После ЛЮБОГО патча, независимо от изменённого модуля, перед отправкой в GitHub
или публикацией выполняется весь штатный набор. Это относится также к tooling,
тестам и документации. Правило обязательности задано в [AGENTS.md](../AGENTS.md#статус-проверки-и-поставка).
Поставка локального патча/ZIP для проверки допустима до полного прогона только
с явным статусом «не полностью проверен»; это не разрешение отправки в GitHub.

1. Завершить правки и выбрать окончательную рабочую папку с проверяемыми исходниками.
   Фокусные проверки во время разработки полезны, но не заменяют следующие этапы.
2. Запустить полный `scripts/local-check`: debug/release и `qualityCheck` всех
   production-модулей, включая unit-тесты.
3. Выполнить все три отдельных Python-набора: `scripts/tests`,
   `update/publishing/tests` и `update/publishing/tools/tests`.
4. С разрешённой ADB-отладкой на подключённом ARM64-устройстве либо совместимом
   эмуляторе запустить полный `scripts/device-smoke`, без фильтра классов/методов
   и без ограничения изменённым модулем. Он охватывает все текущие модули с
   `src/androidTest`: app, data/database, update, core/ui, core/media, feature/composer,
   feature/thread, feature/applock. При добавлении нового AndroidTest-модуля
   обновить оба device-smoke-скрипта; список должен оставаться полным.
5. Проверить свежие результаты ВСЕХ этапов и модулей, затем дополнительные
   сценарии изменённой подсистемы и применимые native/host/performance-проверки.
   Только после разбора результатов и отдельного разрешения владельца переходить
   к [процессу отправки](RELEASE_PROCESS.md). Не объединять проверку с автоматическим
   вызовом publisher сразу после последней команды.

Windows PowerShell, из окончательной рабочей папки:

```powershell
& {
    $ErrorActionPreference = "Stop"
    & ".\scripts\local-check.ps1"
    if ($LASTEXITCODE -ne 0) { throw "LOCAL CHECK failed" }

    python -B -m unittest discover -s scripts/tests -v
    if ($LASTEXITCODE -ne 0) { throw "scripts/tests failed" }
    python -B -m unittest discover -s update/publishing/tests -v
    if ($LASTEXITCODE -ne 0) { throw "publishing/tests failed" }
    python -B -m unittest discover -s update/publishing/tools/tests -v
    if ($LASTEXITCODE -ne 0) { throw "publishing/tools/tests failed" }

    & ".\scripts\device-smoke.ps1"
    if ($LASTEXITCODE -ne 0) { throw "DEVICE SMOKE failed" }
}
```

Linux/macOS — аналогичная цепочка с остановкой при ошибке:

```sh
sh -ec '
./scripts/local-check.sh
python3 -B -m unittest discover -s scripts/tests -v
python3 -B -m unittest discover -s update/publishing/tests -v
python3 -B -m unittest discover -s update/publishing/tools/tests -v
./scripts/device-smoke.sh
'
```

Команды не отправляют изменения и не публикуют релиз. Успешный exit code блока
ещё не заменяет проверку отчётов и не означает «публиковать разрешено».
Это инструкция запуска, а не новый технический блокиратор существующего publisher.
При создании помощников выпуска эту последовательность нужно сохранить явно;
старые внешние ZIP-помощники от изменения документации автоматически не обновляются.

### Критерии полного результата

- Для каждого штатного набора/модуля есть результат текущего прогона. `LOCAL CHECK`
  не означает исполнения Android-тестов; APK, сборка тестового APK и успешный Actions
  не доказывают прохождение на телефоне. Отчёт только app не заменяет остальные модули.
- Android JUnit XML находятся в `<module>/build/outputs/androidTest-results/connected/`,
  HTML — в `<module>/build/reports/androidTests/connected/`. JVM XML —
  в `<module>/build/test-results/`.
  Для Python сохраняется итог каждого запуска и exit code.
- Перед телефонным прогоном записать время начала и состав исходников/патчей;
  сверить свежесть файлов, устройство, классы/методы, число tests, failures, errors
  и skipped. Не суммировать старые, повторные или относящиеся к другому устройству
  XML как новый успех. Отсутствие XML, ноль реально выполненных обязательных тестов,
  незапущенный модуль и несовпадение ожидаемых сценариев — не PASS.
- Failures/errors должны отсутствовать. Любой skipped требует разбора причины и
  явного решения владельца; до этого полный PASS не заявляется и отправка заблокирована.
  Уже известная ошибка не становится допустимой только потому, что патч в другом модуле.
- При FAIL сохранить отчёт/stack trace/logcat, найти причину и исправить её.
  Нельзя убрать assertion, отфильтровать класс, добавить suppression, вернуть старый
  XML или просто увеличить все таймауты ради зелёного прогона.
- После исправления или другой правки проверяемых исходников повторить всю цепочку,
  а не только упавший тест. Итог относится к окончательному содержимому, не к имени
  папки или старому маркеру PASS. При сборке финальной Git-копии заново убедиться,
  что в неё вошли именно проверенные изменения и не появилось непроверенных правок.
- Нет SDK, устройства, fixture или иной нужной среды — записать блокер и статус
  «не полностью проверен». Это не разрешение пропуска и не основание для push.
  Отдельные native-host наборы требуют своей среды/внешних файлов: область и команды
  описаны в [проверках плеера](../video-ffmpeg/tests/README.md); общий прогон их не имитирует.

Перед отправкой показать владельцу: ревизию/состав изменений, команды и exit codes,
устройство/Android, сводку по каждому набору/модулю, failures/errors/skipped,
ссылки или пути к свежим отчётам, дополнительные проверки и ограничения.
Только после успешного разбора запрашивается разрешение отправки.
Штатная генерация пяти release-файлов publisher и проверки Actions сохраняются;
они не отменяют предварительную проверку исходников на устройстве.

## Полная локальная проверка

Windows PowerShell:

```powershell
.\scripts\local-check.ps1
```

Linux/macOS:

```sh
./scripts/local-check.sh
```

Скрипт останавливает daemon, собирает debug/release и запускает qualityCheck.
Только завершение всей цепочки даёт `LOCAL CHECK: PASS`.
Состав и ограничения проверок — в [QUALITY.md](QUALITY.md).
Это только локальный этап [обязательной цепочки](#обязательный-порядок-после-каждого-патча), не разрешение публикации.

## Проверка на устройстве

Подключить ARM64-устройство с разрешённой ADB-отладкой либо совместимый эмулятор:

```powershell
.\scripts\device-smoke.ps1
```

```sh
./scripts/device-smoke.sh
```

Скрипт обязательно запускается после каждого патча и выполняет connectedDebugAndroidTest для app, data/database, update, core/ui,
core/media, feature/composer, feature/thread и feature/applock. Наличие compiled AndroidTest APK
не означает исполнение тестов на устройстве. Целевые ручные сценарии выбираются
по изменённой подсистеме, замеры — по [протоколу performance](contracts/PERFORMANCE.md).

## Изоляция приложения при device-тестах

Debug устанавливается как **Pawchan Debug**: `com.solthariel.pawchan.debug`,
тестовый APK — `com.solthariel.pawchan.debug.test`. Release называется Pawchan и
использует основной package `com.solthariel.pawchan`, без суффикса. Его APK
обновляют существующий Pawchan только при совпадении сертификата и
подходящем versionCode; переход с прежнего `.dev` автоматически не переносит данные.
У debug отдельные настройки, БД, файлы и PIN; данные release туда не переносятся.

Перед установкой debug или connectedDebugAndroidTest задача
`:app:verifyDebugPackageIsolation` проверяет реальные merged-манифесты: оба
package, instrumentation target и authorities провайдеров. Если они пересекаются
с release, выполнение останавливается до установки тестовым раннером.
Нельзя обходить эту задачу через `-x`, вручную менять applicationId или запускать
старые AndroidTest APK с прежним target. Local `assembleRelease` с debug-подписью
по-прежнему НЕ предназначен для установки поверх официального релиза.

На основном телефоне не запускайте `adb uninstall com.solthariel.pawchan` и не
удаляйте обычный Pawchan ради тестов. Для первого прогона новой изоляции предпочтительно
тестовое устройство. Отдельный package защищает данные release, но тестовый раннер
может очищать или удалять сам **Pawchan Debug**. Для каждого прогона проверяйте
XML-отчёт: нужные классы, число тестов, failures/errors/skipped — одной строки
BUILD SUCCESSFUL недостаточно.

## Быстрая обратная связь

Для треда на Windows есть `scripts/check-thread.ps1`: KtLint, thread unit tests
и thread Detekt. Это не полный LOCAL CHECK. Форматирование — отдельная
изменяющая исходники операция `scripts/format-kotlin.ps1` / `.sh`; проверка
качества не должна незаметно форматировать или подавлять диагностику.

Для документационных изменений проверить ссылки, сохранность перенесённых
требований и отсутствие изменений кода/версии. Одни проверки документации не
дают полного LOCAL CHECK. Нет SDK или устройства — указать ограничение честно.

## Библиотеки mpv и исторический инструмент FFmpeg/dav1d

Debug и release включают готовые библиотеки mpv из
`video-ffmpeg/src/main/jniLibs/arm64-v8a`. Перед сборкой Gradle сверяет их с
`video-ffmpeg/mpv-libraries.sha256`, а после сборки проверяет состав APK.
Устройство должно поддерживать arm64-v8a. Для сборки не нужно пересобирать mpv.

Происхождение, исходники JNI и команда его пересборки описаны в
[BUILD-PROVENANCE.txt](../third-party/libmpvkt/BUILD-PROVENANCE.txt). Если
пересобирается JNI-библиотека, необходимо осознанно обновить её контрольную
сумму и заново выполнить проверки на устройстве. До распространения release
нужно проверить комплект лицензий и соответствующих исходников mpv.

Исторический инструмент сборки FFmpeg/dav1d, неиспользуемые старые заголовки
и архивы исходников удалены; они не собирали используемый mpv. Для пересборки
JNI сохранён только необходимый заголовок FFmpeg `libavcodec/jni.h` в
`third-party/libmpvkt/jni-source/include`, вместе с его уведомлением. Исторические
сведения о происхождении сохранены в `docs/history/FFMPEG_NATIVE_BUILD_NOTICE.md`
и `docs/history/ffmpeg-native-dependencies.json`. Проверка удалённого инструмента
не входит в `qualityCheck`. Источники для распространяемых библиотек mpv
требуют отдельной проверки перед выпуском.
