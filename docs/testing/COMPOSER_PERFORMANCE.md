# Измерение изменения ComposerStatusLine

## Область и ограничения

Это Macrobenchmark реального internal `ComposerStatusLine`, а не копия его реализации.
Отдельное приложение `com.solthariel.pawchan.performance` содержит синтетическую offline-сцену;
обычные Pawchan/Pawchan Debug и их данные не удаляются. Activity живёт только в benchmark
source set владельца компонента; публичное production API не расширяется.

Target: `benchmark`, non-debuggable, profileable, R8 и resource shrinking включены,
debug signing. Версии SDK/Compose/Kotlin совпадают с проектом. Отличия от приложения:
изолированный host вместо PawchanApplication, нет репозитория, сети, реальных черновиков,
каталога, треда и изображений; Full AOT вместо release-профиля. Поэтому это НЕ доказательство
производительности всего Pawchan, запуска или холодных кэшей.

Две временные копии текущего дерева создаются вне checkout. Candidate неизменён.
Baseline отличается только удалением `.align(Alignment.Top)` у правого блока статуса;
это контрфактический замер одной правки, не воспроизведение старого релиза целиком.
В `source-pair.json` сохраняются SHA-256 файлов обеих копий и единственный различающийся путь.
Старые build/results, .git и файлы ключей не копируются. Сами рабочие копии в ZIP не попадают.

## Сценарий и протокол

- Физический телефон Android 12+, один подключённый/авторизованный adb device.
- Одинаковые яркость/частота, питание, настройки и тепловое состояние до/после;
  телефон разблокирован, руками его во время итераций не трогать.
- Обе сборки компилируются заранее, затем перед каждым запуском пауза для остывания.
  Сохраняются thermal/display/battery/power/system-settings/getprop до и после.
  Скрипт ждёт thermal status 0/1; это НЕ заменяет сравнение температур и частоты в отчёте.
  Системные настройки, ограничения температуры и root-параметры не меняются.
- Одна сцена: viewport 240 × 320 dp; тот же длинный текст ошибки, что в UI regression test.
- Full AOT; каждый повтор — новый процесс, запуск и два одинаковых цикла прогрева ВНЕ замера.
  Затем 10 циклов: показать ошибку → swipe вверх/вниз → убрать ошибку.
  Пять измеряемых повторов baseline, затем пять candidate. Порядок фиксирован и указан;
  при спорном результате повторить серию с обратным порядком вручную после согласования.
- Только прогретые переходы текста/компоновки/прокрутки. Старт процесса не измеряется.
  Нет внешних запросов/данных; изображения не загружаются, холодный сценарий не заявляется.
- AndroidX Macrobenchmark 1.4.1, FrameTimingMetric; UiAutomator синхронизируется по state marker.
  Ошибки benchmark-конфигурации/заряда/emulator не подавляются.

## Запуск и порядок проверки

Из пакета патча запускать `Check-Performance.ps1 -ProjectPath <корень>`.
Он проверяет установленный payload, выполняет полный `scripts/local-check.ps1`, все три
Python suites (включая новые тесты подготовки/валидатора), проверку валидатора XML,
все семь модулей `connectedDebugAndroidTest` с принудительным свежим прогоном, затем
`Measure-ComposerPerformance.ps1`. Любая ошибка останавливает следующий этап;
finally собирает ZIP с результатами уже выполненных этапов, включая частичные performance reports.

Для отдельного повторного измерения после полного прогона на том же неизменённом исходнике:

```powershell
& .\scripts\performance\Measure-ComposerPerformance.ps1 -ProjectPath $PWD.Path -OutputPath "$env:TEMP\Pawchan-perf-новый-уникальный-каталог"
```

Это не обход полного release gate: после новой правки полный цикл обязателен снова.
Нужны Python 3, PowerShell, adb/Android SDK, JDK проекта. Без Android SDK агент может проверить
host-скрипты/форматирование, но не объявляет Android compilation/device/performance PASS.

## Артефакты и принятие результата

В общем ZIP: fresh XML/HTML всех 375 штатных device-тестов, run-summary/device-validation,
performance-summary/source-pair, для обеих сборок benchmarkData.json, пять Perfetto traces,
инструментальные отчёты, R8 mapping и device logs. APK тестового модуля может попасть в outputs.
Временные рабочие копии оставляются вне checkout для диагностики, их путь печатается.

Валидатор требует пять непустых массивов `frameDurationCpuMs`/`frameOverrunMs`, совпадение
числа кадров, конечные числовые значения, нужный testcase без skip/failure/error,
единственный JSON и все пять непустых trace-файлов из его profilerOutputs.
Структурная проверка файла trace не заменяет его открытие/анализ в Perfetto.
Сохраняются сырые повторы; производные p50/p90/p95/p99 рассчитаны линейной интерполяцией
по каждому повтору и pooled, доля кадров с `frameOverrunMs > 0` — по каждому повтору.
Количество кадров явно приведено; малый объём не позволяет уверенных выводов о хвостах.

**Допуски ещё не согласованы. Никакой performance PASS скрипт не выдаёт.** До оценки
согласовать метрики и допустимые колебания, проверить refresh/thermal/cache сопоставимость,
просмотреть trace для повторяемых выбросов (Main/RenderThread/GC/text layout/GPU по доступности).
Причину нельзя выводить из одного перцентиля. При плохой сопоставимости повторить замер.
Успешная instrumentation означает только сбор результатов, не отсутствие регрессии.

Не отправлять публично отчёты без просмотра: XML/logcat/device logs могут содержать пути,
идентификатор устройства и диагностические данные. Этот патч не меняет версию и не выполняет
commit, push, release-request или публикацию. После разбора всех проверок нужно разрешение владельца.

## Диагностика benchmark-инфраструктуры перед полным финальным циклом

Пока исправляются ошибки настройки benchmark-модулей, сначала запускать из пакета fix2
`Preflight-Performance.ps1 -ProjectPath <корень>`. Это НЕ release gate и НЕ замена полным тестам.
Он выполняет четыре unit tests backup-ресурсов, сборку target/test benchmark APK, Lint
трёх вариантов target и benchmark-варианта composer, строгий Detekt затронутых Kotlin-модулей,
затем диагностический baseline/candidate Macrobenchmark (5+5) в отдельных копиях.
У com.android.test нет обычной задачи lint: test APK компилируется, Kotlin проверяется Detekt.

Preflight не запускает app LOCAL CHECK, все Python suites и семь модулей/375 device tests.
В его summary эти этапы явно NOT_RUN. Ни performance PASS, ни разрешения на публикацию
успешный preflight не даёт. После разбора полученного ZIP, когда инфраструктура исправна,
на неизменённом финальном дереве отдельно запускается Check-Performance.ps1 ИЗ ПАКЕТА FIX2:
полный LOCAL CHECK → все Python suites → 375 phone tests → финальные замеры → ручной review.
После новой правки окончательный полный цикл остаётся обязательным. Ошибки Lint не подавляются.

Benchmark host использует те же правила запрета backup, что основное приложение: legacy
fullBackupContent и Android 12+ dataExtractionRules с исключением cloud/device-transfer данных.
Основной manifest приложения не меняется.

## Windows export fix3

Временные копии теперь находятся в коротком `%USERPROFILE%\pwc\<10 hex>`, не в длинном
TEMP/Pawchan-perf-work-GUID. Перед сборкой/замером планировщик проверяет ожидаемые
artifact paths по модели/версии телефона: бюджет 240 UTF-16 единиц. При превышении —
остановка ДО замера с предложением короткого WorkRoot/OutputPath. Reparse points
не используются, каталоги не удаляются, настройки Windows/реестр не меняются.

Raw JSON/traces копируются в `<variant>/raw` без глубокого AGP-поддерева.
artifact-copy-map.json сохраняет исходные пути и SHA-256. Имена-дубликаты не перезаписываются.
XML/HTML и mapping сохраняются отдельно. Неполный экспорт остаётся ошибкой, не PASS.

После успешного targeted build/Lint fix2 для диагностики экспорта запускать
`Measure-Only.ps1` ИЗ ПАКЕТА FIX3: только сборки копий и новые baseline/candidate 5+5.
Нет app LOCAL CHECK, всех Python suites, повторного Lint/Detekt или 375 device tests.
Это не заменяет будущий полный финальный gate. Старый baseline без raw-файлов
не используется как численное доказательство. Результаты требуют review/согласованных допусков.

## Контроль порядка измерений

`Measure-ComposerPerformance.ps1` поддерживает `-MeasurementOrder CandidateFirst`:
сначала candidate (с align Top), затем baseline (без align Top). По умолчанию
`BaselineFirst` сохраняет прежний порядок. Оба APK всё равно собираются до первого
охлаждения/измерения. Смысл вариантов, production-код, сценарий, пять повторов,
валидация JSON/XML/traces и короткие пути не меняются.

Из пакета reverse запускать `Measure-Reverse.ps1` после `Apply-PerformanceReverse.ps1`.
Он проверяет хеши установленного дерева, запускает только пять контрактных тестов
порядка и девять тестов путей, затем новую серию candidate → baseline. Фактический
порядок записывается в performance-summary.json; отчёты не смешиваются со старыми.
Это диагностический контроль эффекта порядка, не полный release gate и не доказательство
причины различий. Не запускать 375 тестов повторно на этом этапе. До публикации
необходим отдельный полный финальный цикл на окончательном дереве и ручной review.
Повторный запуск с BaselineFirst сам по себе не является сбалансированным исследованием.

## Диагностический протокол PAW_DIAGNOSTIC_V1

Из нового пакета: Apply-PerformanceDiagnostic.ps1, затем Measure-Diagnostic.ps1.
Только targeted host-тесты и сборки + candidate/baseline 5+5; не LOCAL CHECK/375 тестов.
Production-код не меняется. Новые observers находятся только в src/benchmark.
Обычный запуск не включает observers. Флаг -Diagnostics включает их одинаково
в обоих исходных вариантах; значения сохраняются отдельно в diagnostic ZIP и
measurement-mode.json. --diagnostic обязателен для валидации этих наблюдений.
Их нельзя смешивать с исходными численными замерами или использовать для PASS.

Target-процесс в Perfetto: paw.toggle.long/short (только обработчик изменения state,
НЕ вся последующая recomposition), paw.measure.long/short (измерение потомка),
paw.place.long/short (размещение), paw.draw.long/short (запись рисования содержимого),
paw.scroll (асинхронный интервал наблюдаемого isScrollInProgress), paw.scrollY (counter).
Направление прокрутки определяется знаком изменения scrollY. Observer имеет задержку
планирования и overhead; маркеры не являются полным CPU-профилем компонента или
точным моментом физического касания. Отсутствие маркеров в trace требует диагностики,
не считается отсутствием проблемы. Энергия и итоговая плавность всего приложения не оцениваются.

При исключении сохраняются pawdiag-failure.png, pawdiag-failure-ui.xml, pawdiag-failure.txt
через additionalTestOutputDir. Это best effort после ошибки, не повтор действия и не
подавление исключения. Исходная ошибка остаётся фатальной. Уведомления заранее скрыть
вручную; телефон разблокирован, одинаковые настройки, охлаждение перед каждой серией.
Если среда не позволяет capture, причины остаются в logcat. Публикации и PASS нет.
