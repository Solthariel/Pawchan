# Единый процесс выпуска Pawchan

## Контракт

Публикации разрешены только от GitHub-аккаунта Solthariel и запускаются push-коммитом в master при изменении
update/publishing/release-request.json. Workflow остаётся
.github/workflows/publish-release.yml с именем **Publish signed release**.
`run-name`, ручного workflow_dispatch, tag-trigger и дополнительных workflow нет.
Название строки — сообщение коммита; подпись Commit … pushed by … формирует GitHub.
Номер и статус запуска назначает GitHub: старые номера не переиспользуются,
currently running после завершения естественно сменяется на completed/failed.

## Обычный выпуск

Работайте в Git-папке из установщика, а не в ZIP без .git.
Изменения приложения должны быть просмотрены и сохранены коммитами.
Секреты, локальный SDK, .idea и кеши не коммитятся.
Подготовьте реальный changelog в UTF-8 вне рабочей папки, например в Downloads.

```powershell
.\scripts\Publish-Release.ps1 -Change patch -NotesFile "$env:USERPROFILE\Downloads\release-notes.txt"
```

Вместо patch используйте minor/major по смыслу изменений. Команда проверяет
master, origin, чистоту tracked-файлов, отсутствие забытых untracked-исходников
и актуальность ветки. Явно задаёт автора И коммиттера Solthariel с GitHub noreply,
не меняя глобальную конфигурацию. Показывает версию/code и просит ввести YES.
После подтверждения готовит и коммитит только пять файлов метаданных/changelog,
затем делает обычный push. Нет git add ., force push, amend или reset.
Локальные feature-коммиты могут быть впереди origin/master; ветка не должна отставать.
После ошибки commit/push проверяйте состояние: команда намеренно не сбрасывает файлы.

Actions: read-only preflight → полный штатный package-release.sh (LOCAL CHECK,
qualityCheck, release build) → проверка подписи и SHA → плоский source ZIP →
создание постоянного целевого тега на текущем коммите → draft → проверка всех скачанных обратно файлов → promotion → атомарный Git-коммит ленты.
На компьютере нужен Git/Python и обычная авторизация push; gh/winget/PAT не нужны.
Ключи подписи остаются в GitHub Secrets и временной папке существующего build-step.

## Повтор после сбоя

```powershell
.\scripts\Retry-Release.ps1
```

Команда создаёт обычный коммит с новым revision того же запроса. Версия/code
НЕ меняются; запускается тот же Publish signed release с подписью push-коммита.
Нужно подтвердить YES. Ручное редактирование JSON не требуется.

| Обнаруженное состояние | Действие |
|---|---|
| Релиза ещё нет | Сборка и проверка, затем создание draft |
| Совместимый частичный draft | Пересборка; сверка существующих файлов; загрузка только отсутствующих |
| Draft от другого кода/с другими байтами | Остановка без удаления/перезаписи |
| Публичные файлы есть, история ленты ещё не обновлена | Только проверка файлов и восстановление ленты, без Java/SDK/сборки |
| Публикация и лента уже завершены | Проверенный no-op, без новой сборки/загрузки/коммита ленты |
| APK отличается от уже опубликованного hash | Остановка; автоматическая замена запрещена |
| История говорит «опубликовано», а релиз удалён | Остановка, не скрытая пересборка |
| Есть более новый публичный выпуск | Устаревший запрос остановлен |

Проверки существующего draft не предполагают, что новая пересборка будет побайтно
идентична. Если это не так, draft НЕ затирается: нужна отдельная проверка оператором.
Если APK уже публичный, для восстановления используется именно этот APK, не новый.

## Гарантии и границы

- Нет автоматического удаления релизов/assets/тегов, перемещения тегов и перезаписи APK.
- Завершённые одноразовые инструменты перевыпуска 0.1.29 и косметической правки
  старого описания 0.1.20 удалены. Обычный выпуск не редактирует старые release bodies.
  Старое поле запроса в уже опубликованной версии не даёт права повторной замены.
- Старые выпуски до versionCode 30 включительно могут иметь только APK и SHA.
  Они проверяются как исторические; новые выпуски обязательно содержат четыре assets:
  APK, APK.sha256, source.zip, source.zip.sha256.
- Именной source.zip содержит файлы проекта непосредственно в корне. Автоматические
  Source code (zip/tar.gz) GitHub имеют свою верхнюю папку — это неизменяемое поведение GitHub.
- Существующая история changelog сохраняется, новая запись добавляется только один раз.
  Лента/история/новый changelog записываются одним Git-коммитом после проверки release.
- Push ленты повторяется не более трёх раз. При потерянном ответе успешного push
  следующий проход читает удалённое состояние и не дублирует запись.
  Конфликт кода/версий не обходится; force push не используется.
- Release API и Git push НЕ являются одной транзакцией. Во время сбоя лента может
  отставать. Восстановление — Retry-Release, а не удаление рабочего релиза.
- Уже завершённый чужой запуск/номер/подпись не переименовываются этим патчем.
- Нужны существующие signing secrets, доступ к GitHub и права contents:write.
  Ограничения GitHub/сети не отменяются. Workflow ограничен actor Solthariel, а entrypoint проверяет автора и коммиттера
  исходного коммита. Push с другой авторизацией не опубликует релиз. Настройки
  самого workflow администратор репозитория, разумеется, может изменить.

## Проверка изменений процесса

```sh
python3 -m unittest discover -s update/publishing/tests -v
python3 -m unittest discover -s update/publishing/tools/tests -v
```

Тесты GitHub API используют модель сервиса, не реальную публикацию.
Фактические clone/commit/push и потерянный ответ push проверяются отдельно
на локальном bare-remote. Они не заменяют подпись APK и полный Android LOCAL CHECK.
Поведение приложения, правила качества, version/code и changelog этим патчем не меняются.

## Разбор сбоя запуска №41

В предоставленном логе сборочный шаг завершён, а финальный шаг остановился на
HTTP 403 Resource not accessible by integration при создании временного staging
release на старом коммите. Contents:write у GITHUB_TOKEN в логе присутствует.
Удаления публичного релиза не произошло. Новый механизм не использует staging
теги или скрытый перевыпуск старого APK: целевой тег нового выпуска закрепляется
на текущем commit перед созданием draft. При возобновлении используется этот же
тег; тег не перемещается. Это не отменяет иных ограничений токена/репозитория.
Запуск №41 этим инфраструктурным патчем не переписывается и не объявляется успешным.
Ранее опубликованная 0.1.29 сохраняется. Для неё Retry-Release выполнит проверенный
no-op, а не выдаст старый APK за новую сборку. Отдельная замена опубликованного APK
не входит в обычный процесс и требует отдельного решения.
