# Единый процесс выпуска Pawchan

## Контракт

Публикации разрешены только от GitHub-аккаунта Solthariel и запускаются push-коммитом в master при изменении
update/publishing/release-request.json. Workflow остаётся
.github/workflows/publish-release.yml с именем **Publish signed release**.
`run-name`, ручного workflow_dispatch, tag-trigger и дополнительных workflow нет.
Название строки — сообщение коммита; подпись Commit … pushed by … формирует GitHub.
Номер и статус запуска назначает GitHub: старые номера не переиспользуются,
currently running после завершения естественно сменяется на completed/failed.

## Обязательная проверка до отправки

После каждого патча действует [полный порядок проверки](DEVELOPMENT.md#обязательный-порядок-после-каждого-патча)
и [чек-лист готовности](RELEASE.md): LOCAL CHECK всех модулей → все три Python-набора →
весь device-smoke → проверка свежих результатов всех модулей → разрешение владельца.
Тесты только изменённой подсистемы или одного app не заменяют полный прогон.

До этого запрещён переход к отправке изменений в GitHub, созданию release-request,
`Publish-Release`, подтверждению `YES` и публикации. При ошибке, отсутствующей
среде/отчёте или неразобранном skipped отправка останавливается; после исправлений
весь набор выполняется заново. Существующие известные FAIL не исключаются молча.
Генерация метаданных штатным издателем и повторные проверки Actions остаются
обязательными, но не подменяют предварительные телефонные тесты.

Это требование процесса. Текущий `Publish-Release.ps1` сам полный телефонный
прогон и проверку всех XML не выполняет; этот документационный патч не добавляет
технического блокиратора. Агент/оператор и новые помощники выпуска обязаны
соблюдать последовательность до вызова издателя, а не считать запрос YES проверкой.
Если помощник создаёт свежий Git-клон, нужно подтвердить состав конечных исходников;
при непроверенных изменениях выполнить весь набор в финальной папке до отправки.
Старые внешние помощники не обновляются от изменения этой инструкции.

Нельзя писать «все тесты прошли» только по LOCAL CHECK, успешному push, Actions
или наличию релизного APK. Локальный патч можно передать владельцу для проверки
с явными ограничениями; это не разрешение отправки/публикации.

## Обычный выпуск

Работайте в Git-папке из установщика, а не в ZIP без .git.
Изменения приложения должны быть просмотрены и сохранены коммитами.
Секреты, локальный SDK, .idea и кеши не коммитятся.
Подготовьте реальный changelog в UTF-8 вне рабочей папки, например в Downloads.

```powershell
.\scripts\Publish-Release.ps1 -Change patch -NotesFile "$env:USERPROFILE\Downloads\release-notes.txt"
```

Вместо patch используйте minor/major по смыслу изменений. Команда проверяет
master, origin, чистоту tracked-файлов, отсутствие забытых untracked-исходников
и актуальность ветки. Явно задаёт автора И коммиттера Solthariel с GitHub noreply,
не меняя глобальную конфигурацию. Показывает версию/code и просит ввести YES.
После подтверждения готовит и коммитит только пять файлов метаданных/changelog,
затем делает обычный push. Нет git add ., force push, amend или reset.
Локальные feature-коммиты могут быть впереди origin/master; ветка не должна отставать.
После ошибки commit/push проверяйте состояние: команда намеренно не сбрасывает файлы.

Actions: read-only preflight → полный штатный package-release.sh (LOCAL CHECK,
qualityCheck, release build) → проверка подписи и SHA подписанного APK →
создание постоянного целевого тега на текущем коммите → draft → проверка всех скачанных обратно файлов → promotion → атомарный Git-коммит ленты.
На компьютере нужен Git/Python и обычная авторизация push; gh/winget/PAT не нужны.
Ключи подписи остаются в GitHub Secrets и временной папке существующего build-step.

## Windows и выбранная Git-папка

Генераторы новых метаданных и retry-запроса явно записывают LF (`newline="\n"`).
`.gitattributes` также фиксирует LF для JSON публикации, changelog и bundled notes.
Проверка `git diff --cached --check` сохраняется: диагностика не подавляется.
Файлы JSON/changelog и их тестовые фикстуры читаются/пишутся с явным UTF-8.
Вывод Git, содержащий UTF-8 метаданные, также декодируется явно как UTF-8,
а не через локальную Windows-кодировку. Для работы не требуется включать
глобальный UTF-8 mode Python или менять системную локаль.

Перед Git-командами проверяется наличие `.git` непосредственно в корне выбранного
проекта и совпадение `git rev-parse --show-toplevel` с этим корнем. Папка из ZIP
внутри чужого репозитория не считается рабочей копией Pawchan. Переменные
`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR` не могут перенаправить
операции публикации в другое место. Исключение `safe.directory C:/` не требуется
и не добавляется. Для Git worktree допустим штатный `.git`-файл при совпадении корня.

## Продолжение уже подготовленного нового выпуска

Если подготовка метаданных завершилась, но проверка/commit/push оборвались:

```powershell
.\scripts\Publish-Release.ps1 -Resume
```

Это НЕ новая версия и НЕ новый revision. Команда проверяет ровно пять файлов
нового выпуска, воспроизводит их штатным генератором от базового Git-коммита
и сравнивает результат, допуская только разницу LF/CRLF. Опубликованная история
и чужие изменения не перезаписываются. Посторонние tracked/staged/untracked-файлы,
некомплект метаданных, изменённые старые пакеты и отставание/расхождение веток
останавливают продолжение. Каталог сборки и другие штатно ignored-файлы не мешают.

До подтверждения `YES` не нормализуются файлы и не меняется индекс. После подтверждения
план проверяется повторно. Для ещё не закоммиченных метаданных нормализуются только
эти пять файлов, затем сохраняется обычная проверка diff и создаётся один коммит.
Если коммит уже создан, выполняется только обычный push того же коммита с проверкой
автора и коммиттера. Если запрос уже входит в origin/master, новый коммит/push не
создаётся: нужно смотреть существующий Actions run. Это не утверждение о готовности
релиза или успешной публикации ленты. Нет amend, reset, force push и удаления тегов.

Режим рассчитан на стандартный НОВЫЙ выпуск с revision 1, не на незавершённое
ручное редактирование и не на частично подготовленный retry. Установку нового
инструмента сначала нужно сохранить исходным коммитом; он не смешивается с пятью
файлами уже подготовленного запроса. После ошибки ничего не запускайте вслепую.

## Повтор после сбоя

```powershell
.\scripts\Retry-Release.ps1
```

Команда создаёт обычный коммит с новым revision того же запроса. Версия/code
НЕ меняются; запускается тот же Publish signed release с подписью push-коммита.
Нужно подтвердить YES. Ручное редактирование JSON не требуется.

| Обнаруженное состояние | Действие |
|---|---|
| Релиза ещё нет | Сборка и проверка, затем создание draft |
| Совместимый частичный draft | Пересборка; сверка существующих файлов; загрузка только отсутствующих |
| Draft от другого кода/с другими байтами | Остановка без удаления/перезаписи |
| Публичные файлы есть, история ленты ещё не обновлена | Только проверка файлов и восстановление ленты, без Java/SDK/сборки |
| Публикация и лента уже завершены | Проверенный no-op, без новой сборки/загрузки/коммита ленты |
| APK отличается от уже опубликованного hash | Остановка; автоматическая замена запрещена |
| История говорит «опубликовано», а релиз удалён | Остановка, не скрытая пересборка |
| Есть более новый публичный выпуск | Устаревший запрос остановлен |

Проверки существующего draft не предполагают, что новая пересборка будет побайтно
идентична. Если это не так, draft НЕ затирается: нужна отдельная проверка оператором.
Если APK уже публичный, для восстановления используется именно этот APK, не новый.

## Гарантии и границы

- Нет автоматического удаления релизов/assets/тегов, перемещения тегов и перезаписи APK.
- Завершённые одноразовые инструменты перевыпуска 0.1.29 и косметической правки
  старого описания 0.1.20 удалены. Обычный выпуск не редактирует старые release bodies.
  Старое поле запроса в уже опубликованной версии не даёт права повторной замены.
- Новые выпуски прикрепляют только APK. SHA-256 сохраняется в локальной проверке
  сборки и в ленте обновлений; отдельные `.sha256` и именной source.zip не загружаются.
- Уже опубликованные версии до 0.1.33 (versionCode 34) включительно могут содержать
  прежние два или четыре assets. Они проверяются без изменения; после явной ручной
  очистки допускается один APK, но его хеш и размер обязаны совпасть с лентой.
  Новые drafts с посторонними вложениями не чистятся и не перезаписываются автоматически.
- Исходники доступны через стандартные Source code (zip/tar.gz) GitHub с верхней
  папкой тега. Для сборки нужно открыть внутреннюю папку с settings.gradle.kts.
  Native bundle остаётся в Git и проверяется штатным verifyNativeLibraries.
- Существующая история changelog сохраняется, новая запись добавляется только один раз.
  Лента/история/новый changelog записываются одним Git-коммитом после проверки release.
- Push ленты повторяется не более трёх раз. При потерянном ответе успешного push
  следующий проход читает удалённое состояние и не дублирует запись.
  Конфликт кода/версий не обходится; force push не используется.
- Release API и Git push НЕ являются одной транзакцией. Во время сбоя лента может
  отставать. Восстановление — Retry-Release, а не удаление рабочего релиза.
- Уже завершённый чужой запуск/номер/подпись не переименовываются этим патчем.
- Нужны существующие signing secrets, доступ к GitHub и права contents:write.
  Ограничения GitHub/сети не отменяются. Workflow ограничен actor Solthariel, а entrypoint проверяет автора и коммиттера
  исходного коммита. Push с другой авторизацией не опубликует релиз. Настройки
  самого workflow администратор репозитория, разумеется, может изменить.

## Проверка изменений процесса

```sh
python3 -m unittest discover -s update/publishing/tests -v
python3 -m unittest discover -s update/publishing/tools/tests -v
```

Тесты GitHub API используют модель сервиса, не реальную публикацию.
Фактические clone/commit/push и потерянный ответ push проверяются отдельно
на локальном bare-remote. Они не заменяют подпись APK и полный Android LOCAL CHECK.
Эти тесты сами по себе не меняют version/code и не запускают публикацию.
