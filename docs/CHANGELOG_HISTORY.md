# История изменений

Экран открывает локальную историю без ожидания сети и проверяет обновления в фоне.
Показываются все опубликованные версии, в том числе новее установленной. Отметка
«Установлена» вычисляется по versionCode APK, а не по последней записи сервера.

## Данные и отказоустойчивость

При первом запуске используются генерируемые assets из `update/publishing`.
В последующих запусках — проверенная копия `files/changelog/history-v1.json`.
Источник сети — `history-v1.json` рядом с настроенным HTTPS-манифестом обновлений.
Тело истории и ETag записываются атомарно в одном файле. Смена источника сбрасывает
применимость старого ETag. Ответ 304 не перезаписывает данные. Ошибки сети, неверная
схема, дубликаты, пустые заметки, устаревшая или неполная история не заменяют кеш.
Ограничены размер ответа и время запроса. Отмена корутины не подавляется.

Файл `update/feed/history-v1.json` формирует `publish_feed_release.py` только после
успешной публикации APK. Отсечка — код выпущенной версии; записи следующего патча
из publishing не попадут в публичную историю раньше времени. Начальный файл
в этом патче содержит только уже выпущенные версии до 0.1.18 включительно.

История не служит источником установки APK: проверки пакета, подписи, размера и
хеша в существующем механизме обновления не меняются.

## Защита последовательности выпусков (0.1.20)

Запрос может добавлять ровно одну версию после сохранённой опубликованной истории:
следующий Android versionCode и следующий patch, minor или major SemVer. Пакеты
манифеста, реестр версий и запрос должны совпадать. Проверка также сверяет последний
релиз GitHub с опубликованной базой. Пропуск или успешный релиз с незаписанным feed
блокируют следующую публикацию до исправления, а не замалчиваются новым выпуском.

Содержательные пункты старых записей не переписываются: известный пропуск отдельной публикации 0.1.9
не исправляется задним числом и не разрешает новые перескоки. Публичная история
теперь дополняется одной действительно выпущенной версией, а не всеми файлами
заметок с меньшим кодом. Повторная подготовка версии без публикации предыдущей
запрещена; bump_version.py обновляет и release-request.json.

Проверки выполняются до сборки и повторно перед публикацией. При записи feed
повторно проверяется база master, чтобы не затереть более новый выпуск.

## Синхронизация после проверки обновлений (0.1.21)

Экран настроек владеет общим ChangelogHistoryController. Обнаружение обновления
передаёт только versionCode через явный callback UpdatePanel и запускает обновление
истории в scope экрана. Диалог подписан на тот же StateFlow, поэтому новая запись
появляется без перезапуска, в том числе в уже открытом списке.

Если найденный код ещё отсутствует в локальной истории, запрос использует
`release_code` в URL и `Cache-Control: no-cache`, без старого If-None-Match.
Ответ со старшей записью ниже найденного кода или 304 без нужной версии не считается
свежим и не заменяет кеш. Открытие списка повторяет неудавшуюся попытку; обычные запросы после
получения версии снова используют ETag. Это не обходит валидацию схемы, полноты и
ограничения размера. При отсутствии сети остаётся последняя корректная копия.
Номер и дата записи берутся из опубликованной истории, а не выдумываются клиентом.


При входе в «О программе» параллельно стартуют проверка APK и предзагрузка истории.
Проверка принадлежит визиту в раздел, а не lazy-строке или перерисовке: один
UpdateCheckRequest сохраняется в течение визита. Новый вход создаёт новый запрос;
повторное создание строки его не повторяет. Контроллер проверки расположен выше
списка, поэтому прокрутка панели в видимую область не требуется для запуска.
История объединяет параллельные запросы одного визита; открытие и закрытие диалога
после успешной загрузки не обращаются к сети заново. Ошибка не считается успешной
проверкой: открытие списка может повторить её. Обнаружение отсутствующей в истории
версии запускает дополнительную адресную перепроверку, а не доверяет старому 304.
Автопроверка не скачивает APK и не сбрасывает уже скачиваемый/готовый к установке
пакет. Скачивание и установка остаются явными действиями пользователя.


## Явные заголовки разделов

Текст заметок — единый источник для GitHub, bundled assets и feed. Bump добавляет
явный заголовок «Изменения», если заметки начинаются сразу с пунктов. Указанные
автором заголовки «Новое», «Исправления» и другие сохраняются. Publisher до сборки
отклоняет заметки без явного первого раздела или без непустых пунктов; телефонный
fallback остаётся только для совместимости со старыми копиями истории.

Для 0.1.20 разрешена отдельная косметическая коррекция: вставка пропущенного
«Изменения», без изменения пунктов. Исправлены publishing, текст feed и history.
При публикации 0.1.21 существующий GitHub release v0.1.20 получает тот же текст.
План notes-corrections.json ограничен этим выпуском; будущие публикации его не
повторяют. До редактирования сверяются tag_name, отсутствие draft, SHA-256 старого
текста и равенство нормализованного старого текста новому. Любые другие отличия
блокируют автоматическую правку. Уже исправленный текст — no-op.

Меняется только body через gh release edit --notes-file, без --latest, изменения
тега, замены APK/хешей или пересоздания релиза. Поэтому старый выпуск не переносится
вверх списка. Исторический исходный commit/тег и APK намеренно остаются неизменными.
