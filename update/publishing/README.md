# Выпуски и обновления Pawchan

## Версия и порядковый номер

Начальная версия — **0.1.0**, внутренний `versionCode` — **1**. Версии `0.x.y` обозначают начальную
разработку до первого стабильного контракта `1.0.0`; это не обещание стабильности API.
Отметки MVP и номера рабочих патчей не входят в название приложения или APK.

Публичная версия имеет строгий вид `MAJOR.MINOR.PATCH`, без ведущих нулей:

* PATCH: исправление ошибки без новой функциональности и нарушения совместимости.
* MINOR: новая обратно совместимая функциональность; PATCH сбрасывается в 0.
* MAJOR: несовместимое изменение; MINOR и PATCH сбрасываются в 0.

Для серии `0.x.y` несовместимые экспериментальные изменения следует явно описывать
в changelog; при готовности стабильного публичного контракта выпускается `1.0.0`.
В рамках проекта совместимость включает сохранённые данные, настройки, черновики
и поддерживаемые контракты. Само увеличение версии не заменяет миграции.

Порядковый номер `versionCode` независим от трёх чисел SemVer и увеличивается
на 1 для каждого нового выпуска APK: 1, 2, 3… Это не номер запуска приложения
и не счётчик локальных пересборок. В интерфейсе отображается только `0.1.0`; внутренний номер там не показывается.

## Источники данных

* `versions.json` — единственный источник версии, порядкового номера и даты.
* `changelogs/ru/<versionCode>.txt` — описание конкретного выпуска.
* `app/src/main/assets/settings-changelog.txt` — описание текущего выпуска в приложении.
* `manifest/data-v1.json` — опубликованные пакеты с адресами, размером и SHA-256.

Gradle получает версию из `versions.json`. `verifyReleaseMetadata` проверяет
строгий формат, уникальность номеров и согласованность данных текущего выпуска.

## Подготовка следующего выпуска

Создать UTF-8 файл с реальными изменениями, затем из корня проекта выполнить:

```sh
python3 update/publishing/tools/bump_version.py patch --notes release-notes.txt
# Вместо patch выбрать minor или major по характеру изменений.
```

Скрипт увеличивает версию и номер, создаёт changelog, обновляет список изменений
в приложении и добавляет неопубликованный пакет. Старые опубликованные пакеты
не меняются. Дата по умолчанию локальная; для воспроизводимого запуска есть
`--date YYYY-MM-DD`. Скрипт не собирает APK и ничего не публикует.

## Сборка и публикация

После настройки переменных подписания и адреса манифеста:

```sh
./scripts/package-release.sh
# Windows: .\scripts\package-release.ps1
```

Скрипт запускает LOCAL CHECK и подписанную сборку. Имя APK берётся из версии,
например `Pawchan-0.1.0.apk`, а не из номера рабочего архива.

После загрузки APK и changelog:

```sh
python3 update/publishing/tools/update_manifest.py dist/Pawchan-0.1.0.apk --publish --source https://HOST/Pawchan-0.1.0.apk --changelog https://HOST/1.txt
```

Опубликованный подписанный APK неизменяем. Другие байты требуют нового
`versionCode` и собственного changelog. URL, размер и хеш нового APK до реальной
сборки и публикации остаются незаполненными; фиктивные значения не подставляются.

Проверка инструмента версий:

```sh
python3 -m unittest discover -s update/publishing/tests -v
```

## Текущий первый выпуск

`0.1.0` (`versionCode = 1`) — первый выпуск. Повторная сборка тех же исходников
не создаёт новую версию. Подготовка этих исходников не означает публикацию APK.

Единый реестр версий — `versions.json`; Gradle читает номер и код из него.
Текст первого выпуска лежит в `changelogs/ru/1.txt`; идентичная копия для
экрана приложения — `app/src/main/assets/settings-changelog.txt` от корня проекта.
`verifyReleaseMetadata` проверяет совпадение этих текстов, номера и манифеста.
Для будущего отдельного выпуска используйте `tools/bump_version.py` по инструкции выше;
не накапливайте внутренние отчёты об исправлениях в пользовательском списке изменений.
