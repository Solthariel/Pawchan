# Выпуски и обновления Pawchan

## Версия и порядковый номер

Начальная версия — **0.1.0**, внутренний `versionCode` — **1**. Версии `0.x.y` обозначают начальную
разработку до первого стабильного контракта `1.0.0`; это не обещание стабильности API.
Отметки MVP и номера рабочих патчей не входят в название приложения или APK.

Публичная версия имеет строгий вид `MAJOR.MINOR.PATCH`, без ведущих нулей:

* PATCH: исправление ошибки без новой функциональности и нарушения совместимости.
* MINOR: новая обратно совместимая функциональность; PATCH сбрасывается в 0.
* MAJOR: несовместимое изменение; MINOR и PATCH сбрасываются в 0.

Для серии `0.x.y` несовместимые экспериментальные изменения следует явно описывать
в changelog; при готовности стабильного публичного контракта выпускается `1.0.0`.
В рамках проекта совместимость включает сохранённые данные, настройки, черновики
и поддерживаемые контракты. Само увеличение версии не заменяет миграции.

Порядковый номер `versionCode` независим от трёх чисел SemVer и увеличивается
на 1 для каждого нового выпуска APK: 1, 2, 3… Это не номер запуска приложения
и не счётчик локальных пересборок. В интерфейсе отображается публичная версия; внутренний номер там не показывается.

## Источники данных

* `versions.json` — единственный источник версии, порядкового номера и даты.
* `changelogs/ru/<versionCode>.txt` — описание конкретного выпуска.
* `app/src/main/assets/settings-changelog.txt` — описание текущего выпуска в приложении.
* `manifest/data-v1.json` — опубликованные пакеты с адресами, размером и SHA-256.

Gradle получает версию из `versions.json`. `verifyReleaseMetadata` проверяет
строгий формат, уникальность номеров и согласованность данных текущего выпуска.

## Единая команда выпуска и восстановления

Актуальная инструкция: [docs/RELEASE_PROCESS.md](../../docs/RELEASE_PROCESS.md).

Указанные в ней команды запускают существующий Publish signed release через push-коммит в master.
Публикация не запускается вручную и не заменяет ранее опубликованный APK.
bump_version.py остаётся внутренним валидатором подготовки версии, но ручная
цепочка bump/add/commit/push больше не является рекомендуемой инструкцией.
Публичная лента формируется из проверенных release assets; история не дублируется.


## Стиль описаний выпусков

Один текст используется в исходном changelog, описании GitHub Release, истории обновлений
и описании текущего выпуска в приложении. Заголовок — `Версия MAJOR.MINOR.PATCH`.
Разделы идут в таком порядке; пустые разделы не добавляются:

1. **Важно** — сброс данных, ограничения совместимости и действия пользователя перед обновлением.
2. **Изменения** — новые возможности, изменения интерфейса и внутреннего устройства.
3. **Исправления** — устранённые ошибки и их заметный пользователю результат.
4. **Тесты** — добавленные или изменённые проверки; фактический результат запуска указывается отдельно и только при наличии подтверждения.

После заголовка и между разделами — пустая строка. После названия раздела — пустая строка.
Каждый пункт начинается с `- `, занимает одну строку и формулируется законченным предложением.
Не используем вместо разделов «Новое», «Обновлено», «Исправлено», «Проверки» и «Внутренние изменения».
Подготовка версии умеет приводить эти прежние названия и маркеры списков к единому виду;
проверка публикации требует уже нормализованный исходный текст.

Пример структуры (это не готовое описание конкретного выпуска):

```text
Версия 0.2.0

Изменения

- Добавлена новая настройка.

Исправления

- Исправлено сохранение выбранного значения.

Тесты

- Добавлена проверка сохранения настройки.
```

Пишем кратко, по-русски, без рекламных обещаний и перечисления технических задач вместо результата.
Названия API, файлов и форматов сохраняем, когда они нужны для понимания.
Связанные факты можно оставить в одном пункте; изменение поведения и добавленный тест лучше разделить.
«Добавлена проверка» не означает «проверка пройдена». Диагностика не означает ускорение.
Нельзя приписывать старому выпуску исправления следующего выпуска или результаты новых проверок.

### Редактирование исторических описаний

Исправление текста не меняет версию, тег, дату выпуска, APK, подпись или контрольную сумму.
Оно также не создаёт отсутствовавшие релизы. Сначала сверяем факты с существующим описанием
и исходными текстами, затем синхронно редактируем:

- `changelogs/ru/<versionCode>.txt`;
- существующий `../feed/changelogs/<versionCode>.txt` и поле `notes` в истории;
- `../../app/src/main/assets/settings-changelog.txt` — только для текущего выпуска;
- поле `body` соответствующего GitHub Release — отдельно, с авторизацией владельца.

Не переписываем опубликованные APK ради текста: уже установленный APK сохранит старое
встроенное описание до обновления приложения. Изменения исходников сами по себе не обновляют
удалённый GitHub Release или публичную ленту; публикация этих текстов — отдельное действие.
Не заменяем предупреждения о потере данных нейтральными формулировками и не переписываем
исторические отчёты PASS/FAIL. Правила проверок и выпуска остаются в действующей инструкции.
