# Проверки видеоплеера

Основной движок — mpv. Его Android-тесты находятся в `core/media/src/androidTest`:
`MpvVideoEngineRuntimeTest`, `MpvSyntheticFixturesRuntimeTest`,
`MpvSessionRestartRuntimeTest`, `MpvSurfaceHandoffRuntimeTest`,
`MpvSurfaceReferencesRuntimeTest`, `VideoSessionReliabilityRuntimeTest`,
`MpvHttpReplayRuntimeTest`, `VideoBufferHintRuntimeTest` и `MpvFrameTimingRuntimeTest`.
Они требуют подключённого устройства arm64 на Android 11 или новее:

```sh
./gradlew :core:media:connectedDebugAndroidTest
./gradlew :video-ffmpeg:testDebugUnitTest
```

`ProgressiveSourceCleanupTest.kt` проверяет, что закрытие источника не ждёт
зависший HTTP-поток, что живой writer не теряет файл раньше времени и что
временный файл удаляется после остановки загрузчиков и освобождения native reader.
`ProgressiveSourceHostTest.java` — дополнительные host-интеграции с OkHttp и
локальным HTTP-сервером для прогрессивной загрузки. Старые host/JNI-тесты
PawPlayback удалены вместе с их реализацией; они не проверяют mpv.
Host-тест на реальном loopback HTTP загружает трёхсекундный `h264_aac.mp4`, затем
читает его через провайдер одиннадцать раз до EOF. Ожидается один GET; Android-тест
отдельно проверяет десять повторов с настоящим libmpv и ответ 503 с ручным повтором.
Телефонная проверка не заменяется JVM-тестами или одной лишь сборкой APK.

`MpvClipClockRuntimeTest` проверяет на устройстве относительную длительность, первый
кадр, перемотку на паузе, конец и повтор синтетического MP4 с ведущей пустой правкой.
`SavedThumbnailRuntimeTest` в модуле `app` проверяет чтение сохранённого видео и JPEG
через URI, уменьшение картинки и отказ для недоступного или повреждённого файла.
`Mp4EditTimelineTest` и `Mp4LongEditTest` отдельно проверяют простые и неподдержанные таблицы,
повторное чтение/перемотку, сохранение задержки между дорожками и 64-битные длительности.
Тестовые картинки и звук синтетические. Ручная проверка: открыть «Загрузки» после
обновления без удаления старых записей; открыть ролик во встроенном просмотрщике
и проверить начало, середину, конец и повтор. Системный внешний проигрыватель
получает оригинал и может показывать его шкалу иначе.

### Первый кадр и пропуски на телефоне (Windows)

Из корня исходников, на одном разблокированном arm64-телефоне с USB-отладкой:

```powershell
.\scripts\mpv-synthetic-tests.ps1 -MeasurePerformance
```

Два локальных вертикальных H.264: 1080×1920 и 2160×3840, оба 60 кадров/с,
240 кадров, по 4 секунды. Для каждого: один незаписываемый прогрев, затем пять
новых сессий до естественного конца. CSV и logcat сохраняются вне проекта в
`%TEMP%\Pawchan-checks\mpv-…`; команда выводит путь и медиану `first_ms` для каждого файла.
Без флага запускается обычная проверка совместимости.

- `first_ms`: от вызова `open` до первого подтверждённого обновления TextureView
  с видеокадром после `PLAYBACK_RESTART`. Создание движка и подготовка файла не входят;
  это не запуск приложения, не время HTTP-загрузки и не аппаратная метка дисплея.
- `decoder_drops` и `output_drops`: прирост двух разных счётчиков mpv
  (`decoder-frame-drop-count` и `frame-drop-count`) за интервал `from_ms`…`to_ms`
  на шкале ролика. Границы указаны для каждого запуска; пропуски вне окна не посчитаны.
  `NA` означает, что значение неизвестно, а не ноль. Складывать эти счётчики и
  выводить из них фактический FPS нельзя.
- `decoder`, `model`, `api`: фактический режим HW/SW (либо `unknown`), модель,
  версия API Android. В таблицу попадают только десять неповторяющихся результатов
  текущего запуска. Это диагностический тест debug-сборки, а не доказательство
  плавности релиза на всех телефонах. Для сравнения сборок сохраняйте условия
  устройства и следуйте [протоколу производительности](../../docs/contracts/PERFORMANCE.md).

После изменения плеера на реальном arm64-устройстве проверьте:

- Быстрые переходы между соседними видео и возвращение назад; не должно быть
  пауз из-за ожидания завершения старой HTTP-загрузки.
- 20+ переключений между большими файлами: временные `neko-ffmpeg-*.media`
  исчезают после закрытия mpv, память не растёт без ограничений.
- Перемотка у верхнего/нижнего края 48dp строки, с Accessibility/TalkBack.
- PiP → возврат в просмотрщик с сохранением позиции и звукового состояния.
- Включите музыку в другом приложении. Откройте видео с аудиодорожкой в Pawchan
  с выключенным звуком, дождитесь повтора, войдите и выйдите из PiP: музыка не должна
  прерываться из-за ролика. Затем включите звук в Pawchan и снова выключите:
  фокус должен запрашиваться только для слышимого видео. Возобновление музыки
  после освобождения фокуса зависит от самого музыкального приложения.
- Работа на устройстве с `ActivityManager.isLowRamDevice = true`: без
  опережающей загрузки следующего видео.
- Видео H.264 / HEVC / VP8, локальное и медленная/прерванная сеть;
  проверить HW/SW переключение и метаданные после начала воспроизведения.

Это протокол проверки, а не подтверждение её выполнения.
